### Known issues at release

November 16 follow-up: issue 2 below was an incorrect test lookup of another
account's empty feed; the intended account's reminder remained stored. The
profile-aware assertion now passes, including HB extension reload. Issue 1 was
traced to separate manual and automatically mapped GL profiles and remains
unresolved pending explicit destination/mapping handling. The release-time
observations below are retained as history.

1. **Manual-handoff duplicate purchase — medium, product defect, priority for the next release.** After HB's saved purchases are cleared and restored from GL with a manual (Advanced) import, and automatic sharing then runs, GL holds a second Humble record (different item reference, same source) for a purchase it already had, and ownership queries return both. Nothing is lost. Reproduced on every run in Chrome and Firefox, and with the published runtimes (GL 1.0.2 + HB 1.0.3 + FAN 1.0.5) under the current test, so it is not introduced by these candidates. Only the queried title was inspected; how many of the restored records are duplicated has not been measured. The regression test is the default (manual) mode of `scripts/check-purchase-handoff-browser.mjs`, at the `afterQuery` assertion (`assert.deepEqual(afterQuery.results,beforeQuery.results)`); keep it unchanged and expect it to fail until the defect is fixed. Not fixed in this release because the fix belongs in shared purchase-sync code. See [automatic purchase sync](../architecture/automatic-purchase-sync.md#known-issue-duplicate-after-a-manual-restore).
2. **Firefox companion reminder feed arrives empty — unresolved, cause unknown.** In `node tests/firefox.mjs --companions`, installed HB reports "Shared 1 entitlements" to GL, but a few steps later GL's stored feed for HB has no entries (`tests/firefox.mjs`, `received.feed.entries.length`, 0 instead of 1). It fails the same way with the HB 1.0.3 package and with the published GL 1.0.2 + HB 1.0.3, so it predates these candidates. Whether the product or the test is at fault has not been established; treat it as a possible product defect until investigated. See [companion API](../architecture/companion-api.md#known-issue-firefox-reminder-feed-arrives-empty).
3. **Chrome collision timeout — intermittent, probably harness or performance.** `--collision` in Chrome failed 4 of 5 times with HB's 1.1.1 runtime (`b2eabf2`, identical to `6d453b4`) and passed 4 of 4 times with HB at `2c84a02`, `a8489cf`, `9c228ec` and `a7e9dd3`; Firefox passed. An instrumented run located the timeout in `scripts/native-purchase-browser.mjs`, in the second phase's recovery step, where GL's `syncNow` over about 11,000 synthetic records must answer within the harness's fixed 20-second browser-command limit. Every data-integrity assertion in that test (manual import complete, no lost or duplicated purchases in HB or GL) had already passed. The only HB change between the passing and failing commits is per-title purchase counting in Options, which is per title and does no work here (the test has no Library copies), so a causal link is unproven. The timeout was not raised; changing the test needs separate review.

## Data and permission explanations

GL stores validated provider records, account labels, supported purchase/access evidence, contents/reviews and corrections locally. Provider requests use supported signed-in sites; local companions exchange bounded matching data and explicitly authorized saved purchases. There is no developer-operated library collection or analytics service. Optional Open Library/Google Books requests send bibliographic fields externally. Firefox required data is `none`, with optional `websiteContent` only. The Google project API key is still sent directly to Google for API access/quota, not user-account authentication. Consent is explicit and revocable. AMO notes and the public policy must describe this; do not claim Mozilla has formally approved the classification.

Storage/unlimitedStorage support large private libraries; scripting runs supported provider tasks; alarms support jobs/sync/reminders; optional notifications support reminders. Named provider and metadata host access supports those features. No new ordinary host/API permissions were added for metadata consent.

Suggested listing description: "Bring supported digital libraries together in one private, browser-local catalog. Search games, books, audiobooks and video while keeping account copies, ownership/access evidence and source history. Optional Humble Library/Fanatical Library companions add bundle checks and consented purchase sync. Optional online book lookups share bibliographic information with Open Library or Google Books after Firefox permission. Supported provider scopes and access uncertainty remain visible."

The owner must verify all applicable dashboard data categories against the full privacy policy and actual store questions. Do not assert that private checkboxes were reviewed here. No remotely hosted executable code is required.
