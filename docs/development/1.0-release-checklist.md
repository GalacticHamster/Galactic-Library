Order: repair B1–B3 and finish I2 live Firefox testing first; compare completed imports in D1 next; inventory wording in U1 afterward; then settle release decisions and final validation. No calendar estimates.

### B1 premature-completion repair and live retest

**Confirmed root cause:** Full rescan and the read-only listing check use the same traversal. The old completion predicate promoted three quiet bottom-of-scroll passes, with no recognized busy/Load more controls, into a complete snapshot even without independent end evidence. The real export reached a current bottom long before all titles appeared; its page height subsequently grew, and its DOM retained only about 67-72 cards while cumulative distinct membership reached 343. This supports asynchronous batches/recycled cards, not a stable terminal boundary. No nested scroll container was detected in that export. Exact timing of the original unexported 180-item failure remains unknown; no Amazon website change is asserted.

A deterministic synthetic replay with a longer unmarked plateau establishes the failure branch: committed `958fed9` returned a complete 180-item snapshot after 11 polls; repaired code observed all 343 and refused completeness after its bounded traversal. This is a reproduction of the demonstrated mechanism, not a capture of the failed session. The later successful live import does not disprove the race.

**Repair:** The three-poll quiet period is now only a candidate boundary. A full snapshot additionally requires a consistent, explicitly labelled whole-list count in the main content region, reconciled against distinct IDs, with no pending library controls or unvisited vertical lists. Only anchored `All items (N)` or `Purchases & Rentals (N)` summaries outside cards/sidebar/navigation qualify; arbitrary body text, historical counts and manual row counts do not. These summary contracts are exercised with synthetic fixtures; their availability on the user's actual Amazon page has **not** been established. No terminal marker, API, network-idle or hidden application state has been invented or assumed.

Without corroboration, continue traversing across quiet plateaus within the existing 250-pass budget; reaching that budget means **uncertain**, never complete. Full rescan sends no replacement/import and preserves existing records. The read-only check may return all observed titles with `completionConfirmed: false` and no complete snapshot. Current live pages may therefore be unable to perform automatic full replacement even when all 343 titles are observed. This is an acknowledged limitation, not a claim the functional completion problem is solved. A reliable automatic completion guarantee remains unavailable from the evidence in hand.

Traversal retains overlapping viewports and scoped controls, resets/visits separate vertical list containers, and retains virtualized observations. Existing rental/purchase/access parsing, identities, unreadable-card rejection, provider-scoped persistence and backup data remain unchanged. Format-3 diagnostics retain per-pass new/cumulative discoveries, cumulative movie/TV totals, scroll geometry, quiet periods, recognized continuation state, count evidence and explicit stop/confirmation reasons. Exports still contain no titles, product IDs, account information or credentials.

**Quick update:** Its intentionally bounded newest-first strategy stops at the first wholly known rendered group. A bad legacy 180-item baseline can therefore produce zero additions despite older gaps. It is not a recovery scan or independent completeness check. No stored baseline/review is rewritten; the UI now calls it a newest-title check and states that older titles were not fully checked. The prior successful Full rescan flag is not used as end-of-list proof for a new full replacement.

Validation: `node tests/browser.js --release --amazon-video` and the same command with `--firefox` each pass 52 synthetic packaged-browser checks. They cover a virtualized unmarked plateau longer than three passes, late batches, uncertain and counted terminal states, changing/unrelated totals, separate scrollers, repeat full scans, bounded Quick update against an incomplete baseline, read-only exports and production-writer preservation. `npm test` passes 1,681 tests. These are disposable fixtures, separate from the user's live observations. The older Chrome backup's 339 distinct source records (298 movies/41 TV titles) remains a historical comparison, not today's authoritative count or import input.

Live retest (Firefox first, then Chrome parity):

1. Reload the updated extension and Amazon Video **My Stuff > Purchases & Rentals**, with search/filters cleared. Do not restore, merge or otherwise modify either library for this test.
2. Expand **Scan diagnostics**, click **Check listing (no import)** and allow its bounded traversal to finish. Without independently recognizable end evidence this can take roughly three minutes (250 waits of 700 ms plus processing), and should report uncertainty rather than success. Export `GL-amazon-video-scan.json` even when all titles were observed. This check creates no sync lease and writes no records or sync health.
3. Record the observed movie/TV totals, `completionConfirmed`, `countEvidence`, final reason and browser/build. Reaching 343 alone must not set confirmation true; today's manual count was 302 movies/41 TV shows, not an Amazon-provided count. Use the new cumulative counts rather than the last rendered window's card types.
4. With a backup retained, test **Full rescan** in Firefox. If end evidence remains unavailable, expect an explanation that completeness could not be confirmed and no library changes were saved. Verify existing source membership, access states and unrelated records remain intact. A genuine independently corroborated end may permit replacement; verify membership and repeat unchanged before considering it validated.
5. **Quick update** may still report zero new titles at a known newest group; it must say older titles were not fully checked. It must not imply it repaired an incomplete baseline. Preserve authoritative Chrome data; use the read-only check there until a safe full replacement is justified.

B1 remains open pending a demonstrated live completion contract and successful Firefox/Chrome validation, or an explicit release decision about the acknowledged unsupported automatic-completion case. Do not replace this uncertainty with a larger idle threshold or an account-specific expected count.
